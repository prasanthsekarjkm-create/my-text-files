SQL Trace and TKPROF
====================
SQL Trace and TKPROF are tools in Oracle that help with SQL performance tuning by analyzing how SQL statements execute and identifying bottlenecks. Here's a simple explanation of both:

SQL Trace
=========
The SQL Trace facility collects detailed information about the execution of SQL statements. It provides raw data about:
* SQL statements executed.
* Execution time.
* Parsing, execution, and fetching statistics.
* Wait events.

Steps to Enable SQL Trace
Enable SQL Trace at the session or instance level.
Generate a raw trace file.
Use TKPROF to analyze the trace file.
Enable SQL Trace for a Session

-- Enable SQL Trace
ALTER SESSION SET sql_trace = TRUE;

-- Execute your SQL statements here

-- Disable SQL Trace
ALTER SESSION SET sql_trace = FALSE;
Enable SQL Trace for a Specific User
You can enable tracing for a user session using PL/SQL or commands:


EXEC DBMS_SESSION.SET_SQL_TRACE(TRUE);
2. TKPROF
The TKPROF (Trace Kernel PROFiler) utility formats the raw trace file into a readable report. This report helps you understand:

Execution times for SQL statements.
Sorting operations.
Parse, execute, and fetch statistics.
Wait events and resource usage.

Steps to Use TKPROF
Locate the raw trace file (generated in the USER_DUMP_DEST directory).
Run the TKPROF command to generate a formatted report.
TKPROF Command Example

Options:
EXPLAIN: Adds the execution plan of SQL statements.

cursor cache 
===============

cursor cache refers to the shared SQL area in the library cache, part of the shared pool in the System Global Area (SGA). It is used to store information about SQL statements that have been executed. Proper use of the cursor cache can significantly improve database performance by reusing previously executed SQL statements.

How Cursor Cache Works

Soft Parsing:
When a SQL statement is executed, Oracle checks if an identical statement already exists in the cursor cache.
If found, Oracle reuses the existing cursor, avoiding the need to parse the statement again. This is known as soft parsing.
Soft parsing saves CPU resources and improves query performance.

Hard Parsing
If no matching statement is found in the cursor cache, Oracle parses the SQL statement, creates a new execution plan, and stores it in the cache.
Hard parsing consumes more resources, including CPU and memory.

Benefits of Proper Cursor Cache Management
---------------------------------------------
Reduces hard parsing and improves query performance.
Minimizes contention for shared resources.
Optimizes memory usage in the shared pool.

how to solve deadlock
======================
A deadlock occurs in a database when two or more transactions block each other by holding resources the other transactions need. Resolving and preventing deadlocks is essential for maintaining the stability of your database systems.

Use Diagnostic Tools:
In Oracle: Use the V$LOCK and V$SESSION views to identify blocked sessions.

Capture Deadlock Details: Find out which transactions, sessions, or queries are involved.

Kill One of the Transactions
Terminate the Transaction: Identify and kill one of the transactions involved in the deadlock to allow others to proceed.
In Oracle:

ALTER SYSTEM KILL SESSION 'sid,serial#';

Prevent Deadlocks
-------------------
Follow a Consistent Resource Order
-----------------------------------
Ensure all transactions access resources (tables, rows, etc.) in the same order to avoid circular waits.
Example: If transactions A and B both need to access tables T1 and T2, ensure they access them in the same sequence (e.g., T1 first, then T2).

Avoid Long Transactions
-----------------------
Break long-running transactions into smaller, more manageable units.
Commit frequently to release locks sooner.

Use Indexes Efficiently
---------------------------
Ensure proper indexing on frequently accessed columns to minimize the locking of large sets of rows.
Example: Use an index on a column being used in a WHERE clause to avoid full table scans.

Reduce Lock Contention
---------------------
Use appropriate isolation levels to balance concurrency and consistency:
READ COMMITTED: Reduces locking overhead but may allow some non-repeatable reads.
SNAPSHOT ISOLATION: Prevents readers from blocking writers and vice versa.
Avoid SERIALIZABLE unless necessary, as it holds locks for longer periods.

Implement a Timeout
--------------------
Set a timeout for transactions waiting on locks to prevent indefinite waiting:

ALTER SESSION SET DDL_LOCK_TIMEOUT = 30; -- Wait for 30 seconds

Use Row-Level Locking
----------------------
Avoid table-level locks when row-level locks suffice. This minimizes contention between transactions.

To solve and prevent deadlocks:
--------------------------------
-------------------------------

Resolve by identifying and terminating one transaction.
Prevent by:
Following consistent resource ordering.
Optimizing queries and using proper isolation levels.
Avoiding long transactions and reducing lock contention.

To stop a continuously running query in Oracle SQL, you need to identify the session executing the query and terminate it. Follow these steps:

Steps to Stop a Running Query
1. Identify the Running Query
You can check which query is running by querying V$SESSION and V$SQL views.

SELECT s.SID, s.SERIAL#, q.SQL_TEXT, s.STATUS, s.USERNAME
FROM V$SESSION s
JOIN V$SQL q ON s.SQL_ID = q.SQL_ID
WHERE s.STATUS = 'ACTIVE';

SID: Session Identifier.
SERIAL#: Serial number for uniquely identifying the session.
SQL_TEXT: The SQL query being executed.
STATUS: The session's current state (ACTIVE or INACTIVE).
USERNAME: The user who initiated the session.

2. Identify Your Query
From the output, locate the query that is running continuously and note its SID and SERIAL#.

3. Terminate the Query
Use the following command to kill the session associated with the query:

ALTER SYSTEM KILL SESSION 'SID,SERIAL#';
Replace SID and SERIAL# with the values from the previous step.

Example:

ALTER SYSTEM KILL SESSION '101,2021';

4. Forcefully Terminate (Optional)
If the session doesn’t terminate immediately, you can add the IMMEDIATE keyword:


ALTER SYSTEM KILL SESSION 'SID,SERIAL#' IMMEDIATE;

If the query is blocked by another session:


SELECT BLOCKING_SESSION, SID, SERIAL#, USERNAME

NOCOPY hint 
===========
The NOCOPY hint in PL/SQL helps improve performance when passing large data (like arrays, records, or big variables) into procedures or functions. Normally, PL/SQL makes a copy of the data to avoid accidental changes to the original value. But with NOCOPY, it skips copying and directly works on the original data.

Why Use NOCOPY?
It’s faster because it avoids copying large amounts of data.
It’s useful for OUT or IN OUT parameters when you need to send back results from a procedure or function.

If you add NOCOPY, it works directly on the original variable:

sql
Copy
Edit
CREATE OR REPLACE PROCEDURE increase_salary(p_salary IN OUT NOCOPY NUMBER) IS
BEGIN
    p_salary := p_salary * 1.1; -- Increase salary by 10%
END;

Now, the value of p_salary is updated directly, which makes it faster.

When to Use NOCOPY?

Use NOCOPY when passing large data like collections, big objects, or records to avoid slow copying.
Be careful! If the procedure raises an error, the original variable might still get partially updated since no copy exists.

scrollable cursor
===================
A scrollable cursor in Oracle is a type of cursor that allows you to fetch rows in a non-sequential manner. Unlike standard cursors that fetch rows sequentially, scrollable cursors enable navigation both forward and backward through the result set, as well as jumping to specific rows.

Key Features:
Random Row Access:

Navigate to the first, last, next, previous, or a specific row in the result set.
Non-Sequential Fetching:

Provides flexibility for applications that require dynamic row access.
Supported in PL/SQL:

Introduced in Oracle 9i.
Performance Consideration:

Scrollable cursors require more memory as they store the entire result set in the client-side memory or temporary segments.
Declaring a Scrollable Cursor

Key FETCH Options
When using scrollable cursors, you can fetch rows with different options:

FIRST: Fetches the first row of the result set.
LAST: Fetches the last row of the result set.
NEXT: Fetches the next row relative to the current position.
PRIOR: Fetches the previous row relative to the current position.
ABSOLUTE n: Fetches the nth row from the start of the result set (1-based index).
RELATIVE n: Fetches a row that is n rows away from the current position.

                Scrollable Cursor vs Regular Cursor
Feature	Regular Cursor	                  Scrollable Cursor
Navigation	Sequential only	          Forward, backward, specific rows
Memory Usage	Minimal	                  Higher (stores result set)
Flexibility	Limited	                  High
Performance	Faster for simple fetch	  Slower due to overhead
Use Cases	Simple processing	  Complex data navigation

Limitations of Scrollable Cursors

Memory Intensive: Requires more memory to store the result set.
Not Suitable for Large Datasets: Storing large results in memory can degrade performance.
Complexity: Handling scrollable cursors might be complex for very large applications.


DECLARE
   CURSOR emp_cursor IS
      SELECT employee_id, first_name, last_name FROM employees
      ORDER BY employee_id SCROLL;
   emp_record employees%ROWTYPE;
BEGIN
   -- Open the scrollable cursor
   OPEN emp_cursor;

   -- Move to the first row
   FETCH FIRST FROM emp_cursor INTO emp_record;
   DBMS_OUTPUT.PUT_LINE('First Row: ' || emp_record.first_name || ' ' || emp_record.last_name);

   -- Move to the next row
   FETCH NEXT FROM emp_cursor INTO emp_record;
   DBMS_OUTPUT.PUT_LINE('Next Row: ' || emp_record.first_name || ' ' || emp_record.last_name);

   -- Move to the last row
   FETCH LAST FROM emp_cursor INTO emp_record;
   DBMS_OUTPUT.PUT_LINE('Last Row: ' || emp_record.first_name || ' ' || emp_record.last_name);

   -- Move to a specific row (e.g., 5th row)
   FETCH ABSOLUTE 5 FROM emp_cursor INTO emp_record;
   DBMS_OUTPUT.PUT_LINE('5th Row: ' || emp_record.first_name || ' ' || emp_record.last_name);

   -- Move to the prior row
   FETCH PRIOR FROM emp_cursor INTO emp_record;
   DBMS_OUTPUT.PUT_LINE('Prior Row: ' || emp_record.first_name || ' ' || emp_record.last_name);

   -- Close the cursor
   CLOSE emp_cursor;
END;

DIRECT PATH hint(append)----------writes data directly into the data blocks
================
* DIRECT PATH hint is used to optimize the data loading process by enabling the direct path insert mechanism. 
* This method bypasses the conventional insert mechanism and writes data directly into the data blocks
* which improves performance by reducing the overhead of logging and undo generation.

INSERT /*+ APPEND */ INTO table_name
SELECT ...
FROM source_table;

Hint Usage:

The APPEND hint enables direct path insert.
It is applicable for INSERT INTO statements only.

Direct Path Behavior:

Data is written directly into the table’s data blocks, bypassing the buffer cache.
Generates minimal redo and undo logs.
Usually allocates new blocks above the high water mark (HWM).

Prerequisites:

The table should not be part of a cluster or an index-organized table (IOT).
Sufficient space must be available in the tablespace.
If constraints are enabled, they must allow efficient validation.

Performance Benefits:

Faster data loads for bulk insert operations.
Reduced impact on database performance during the operation.

Important Considerations:

The table will be temporarily unavailable for queries until the insert operation completes.
Indexes on the table are updated after the insert operation.
Cannot be used in multi-tenant environments without PARALLEL mode.
Example:

INSERT /*+ APPEND */ INTO sales_archive
SELECT * FROM sales_data WHERE sale_date < SYSDATE - 365;

Parallelism:

You can combine the APPEND hint with the PARALLEL hint for even better performance in large-scale data loading.

INSERT /*+ APPEND PARALLEL (sales_archive, 4) */ INTO sales_archive
SELECT * FROM sales_data WHERE sale_date < SYSDATE - 365;

If a cursor is updating 100 records in a table and another user tries to TRUNCATE the table at the same time, the behavior depends on how Oracle's transaction control and locking mechanisms work. Here's what happens

Key Concepts
TRUNCATE is a DDL Operation:

TRUNCATE is a Data Definition Language (DDL) command, not a DML (DELETE, UPDATE) command.
It immediately commits the transaction and cannot be rolled back.

Locks:
When a cursor updates rows, Oracle applies row-level locks on the rows being updated.
TRUNCATE, however, requires a table-level lock to remove all rows in the table.

Mutual Exclusion:
TRUNCATE cannot proceed if the table is locked by another transaction (like the one updating rows using the cursor).
Similarly, the update cannot proceed if a TRUNCATE has already started, as the table would be locked for the TRUNCATE operation.

Cursor Updates Start First:
===========================

If the cursor begins updating 100 records, Oracle locks those rows for the duration of the transaction.
When the second user tries to TRUNCATE the table, Oracle will block the TRUNCATE operation until the cursor’s transaction completes (either committed or rolled back).
Once the cursor's updates are committed, the TRUNCATE operation can proceed, and all rows (including the updated ones) will be removed.
Result: The updated rows will briefly exist in the table but will be deleted by the TRUNCATE.

TRUNCATE Starts First:
========================

If the TRUNCATE command is executed before the cursor begins updating the rows, the TRUNCATE takes a table-level lock and removes all rows.
The cursor’s update operation will fail because the table will no longer have the rows to update.
Result: No rows will be updated, and the cursor’s transaction will raise an error.

Why This Happens
Oracle enforces table-level locks for TRUNCATE and row-level locks for DML operations like UPDATE.
TRUNCATE is considered a higher-priority operation because it’s a DDL command and commits automatically.

I run one select statement query what happened in background(like oracle architecture)?
======================================================================================
When you run a SELECT statement in Oracle SQL, the Oracle database architecture goes through a series of processes and components to execute the query. Here’s a simplified breakdown of what happens in the background:
SQL Parsing
Shared Pool Check
Generating the Execution Plan(Optimizer)
Executing the Query(SQL Execution)
then checks Buffer Cache
Returning Results (Fetching Data)
Maintaining Consistency (Undo and Redo)

1. Parsing the Query (SQL Parsing)
SQL Parsing: The SQL statement goes to the SQL Parser, where it’s checked for syntax errors and semantics (like column and table names).
Shared Pool Check: Oracle checks the Shared Pool to see if the exact SQL statement is already present. If it’s a “soft parse” (already in memory), Oracle can reuse the execution plan, saving processing time. If not, it proceeds to a "hard parse."

2. Generating the Execution Plan (Optimizer)
The Optimizer evaluates different ways of executing the query and picks the most efficient one based on statistics and available indexes, joins, and access paths.
The chosen plan is stored in the Library Cache, a part of the Shared Pool, for potential reuse.

3. Executing the Query (SQL Execution)
The query plan is now executed. Oracle uses background processes, like the Server Process, to fetch the required data.
Buffer Cache: Oracle checks the Database Buffer Cache (part of the SGA) to see if any blocks containing the requested data are already loaded into memory. If they are, the data is read from the cache (faster retrieval).
If the data isn’t in the Buffer Cache, Oracle retrieves it from the data files on disk, and loads it into the cache for future use.

4. Returning Results (Fetching Data)
The Server Process transfers the fetched data back to the user, row by row.
This data flow continues until the entire result set is returned to user.

5. Maintaining Consistency (Undo and Redo)
Oracle uses the Undo Tablespace to maintain read consistency if other sessions modify data while the query runs.
Redo Logs capture all changes in case of system failure, even though a SELECT statement doesn’t usually modify data.

Summary of Components Involved

SGA (System Global Area): Stores the Shared Pool, Buffer Cache, and Library Cache.

PGA (Program Global Area): Manages memory for the Server Process for each session.

Background Processes: Handle tasks like data retrieval, logging, and cache management (e.g., DBWR, LGWR).

1. What is a PL/SQL Function?
A PL/SQL function is a named block that performs a specific task, usually to return a single value. It can take parameters as input and is often used when a calculation or specific value retrieval is needed.

2. Differences between a Procedure and a Function
Return Value: Functions must return a value, while procedures do not.
Use in SQL Statements: Functions can be called within SQL queries, whereas procedures cannot.
Calling Context: Functions are often used when a result is needed from a query or calculation. Procedures are better suited for performing an action (like updating records).

) RETURN NUMBER

    emp_id NUMBER,

CREATE OR REPLACE FUNCTION get_employees RETURN employee_table PIPELINED IS
BEGIN
    FOR emp IN (SELECT emp_id, emp_name FROM employees) LOOP

CREATE OR REPLACE FUNCTION count_vowels (p_input_string VARCHAR2)
RETURN NUMBER IS
    v_count NUMBER := 0;
BEGIN
    FOR i IN 1 .. LENGTH(p_input_string) LOOP
        IF INSTR('AEIOUaeiou', SUBSTR(p_input_string, i, 1)) > 0 THEN
            v_count := v_count + 1;
        END IF;

END count_vowels;

In PL/SQL, collections are data structures that allow you to store multiple elements of the same type, similar to arrays in other programming languages. They are particularly useful for working with large datasets in memory and are frequently used in bulk operations for improved performance. Here’s a breakdown of the three types of collections in PL/SQL: Associative Arrays, Nested Tables, and VARRAYs.

1. Associative Arrays (Index-by Tables)
Definition: Associative arrays are key-value pairs, where each element is associated with a unique key (index). The keys can be either integers or strings.

Use Case: Useful for dynamic arrays where elements are accessed via custom keys.

Declaration and Example:

1. NO_DATA_FOUND in Collections
Explanation: This exception occurs when you try to access an element in an associative array (index-by table) or a nested table that doesn’t exist.
When It Happens: Associative arrays in PL/SQL allow you to specify arbitrary indices, and nested tables can have sparse indices (non-continuous). If you try to access an index that doesn’t have a corresponding element, you’ll encounter NO_DATA_FOUND.

DECLARE
  TYPE number_table IS TABLE OF NUMBER INDEX BY PLS_INTEGER;
  numbers number_table;
BEGIN
  numbers(1) := 100;
  DBMS_OUTPUT.PUT_LINE(numbers(2)); -- Raises NO_DATA_FOUND as index 2 doesn't exist
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    DBMS_OUTPUT.PUT_LINE('No data found at the specified index.');
END;

Best Practice: Use conditional checks like EXISTS before accessing an associative array to ensure the index exists:

IF numbers.EXISTS(2) THEN
  DBMS_OUTPUT.PUT_LINE(numbers(2));
ELSE
  DBMS_OUTPUT.PUT_LINE('No data at index 2');
END IF;

2. SUBSCRIPT_BEYOND_COUNT-   (index that’s greater than the current collection size)
Explanation: This error occurs when attempting to access an index that’s beyond the current count of elements in a nested table or VARRAY.
When It Happens: It commonly happens in nested tables or VARRAYs when an index that’s greater than the current collection size is accessed.

DECLARE
  TYPE number_array IS TABLE OF NUMBER;
  numbers number_array := number_array(10, 20, 30);
BEGIN
  DBMS_OUTPUT.PUT_LINE(numbers(4)); -- Raises SUBSCRIPT_BEYOND_COUNT
EXCEPTION
  WHEN SUBSCRIPT_BEYOND_COUNT THEN
    DBMS_OUTPUT.PUT_LINE('Index exceeds the number of elements in the collection.');
END;

Best Practice: Use collection methods like COUNT to check the size of the collection before accessing an index.

IF numbers.COUNT >= 4 THEN
  DBMS_OUTPUT.PUT_LINE(numbers(4));
ELSE
  DBMS_OUTPUT.PUT_LINE('Not enough elements in the collection.');
END IF;

3. SUBSCRIPT_OUTSIDE_LIMIT
Explanation: This exception is raised when accessing an index outside the allowable range of a VARRAY, such as a negative index or an index beyond the maximum size.
When It Happens: It applies only to VARRAYs since they have a fixed maximum size.

DECLARE
  TYPE fixed_size_array IS VARRAY(5) OF NUMBER;
  numbers fixed_size_array := fixed_size_array(1, 2, 3);
BEGIN
  DBMS_OUTPUT.PUT_LINE(numbers(6)); -- Raises SUBSCRIPT_OUTSIDE_LIMIT
EXCEPTION
  WHEN SUBSCRIPT_OUTSIDE_LIMIT THEN
    DBMS_OUTPUT.PUT_LINE('Attempted to access an index outside the VARRAY limits.');
END;

Best Practice: Use conditional checks and know the maximum size of the VARRAY when performing index-based operations.

4. VALUE_ERROR in Collections
Explanation: This error occurs when trying to store a value that doesn’t match the declared data type or exceeds the allowed size within the collection.
When It Happens: When you assign a value outside the defined range for elements in a collection, like storing a larger number than the specified precision or using a value that doesn’t match the type.

DECLARE
  TYPE decimal_array IS VARRAY(5) OF NUMBER(3, 2);
  numbers decimal_array := decimal_array();
BEGIN
  numbers.EXTEND;
  numbers(1) := 123.456; -- Raises VALUE_ERROR due to exceeding precision
EXCEPTION
  WHEN VALUE_ERROR THEN
    DBMS_OUTPUT.PUT_LINE('Value exceeds allowed precision or scale in the collection.');
END;

Best Practice: Ensure that values assigned to the collection elements are within the specified range and data type, and consider using constraints if possible.

5. COLLECTION_IS_NULL
Explanation: This exception is raised when trying to perform operations on a null (uninitialized) collection.
When It Happens: Collections must be initialized before use. If a collection variable is declared but not initialized (e.g., using a constructor or assignment), operations like EXTEND, DELETE, or accessing elements will raise COLLECTION_IS_NULL.

DECLARE
  TYPE number_table IS TABLE OF NUMBER;
  numbers number_table; -- Not initialized
BEGIN
  numbers.EXTEND; -- Raises COLLECTION_IS_NULL
EXCEPTION
  WHEN COLLECTION_IS_NULL THEN
    DBMS_OUTPUT.PUT_LINE('Collection has not been initialized.');
END;

Best Practice: Initialize collections right after declaration using a constructor or assignment.

numbers := number_table(); -- Initializes the collection
Additional Tips for Managing Collection Exceptions
Initialize Collections: Always initialize collections to avoid null errors.
Use Collection Methods:
EXISTS: Checks if an index exists.
COUNT: Returns the number of elements.
FIRST and LAST: Return the lowest and highest indices in the collection, useful for loops and boundary checks.
Exception Handling: Use EXCEPTION blocks to catch and handle exceptions gracefully, which allows you to provide user-friendly messages or alternative logic when exceptions occur.

FORALL
------------
The FORALL statement in PL/SQL is used to improve performance by performing bulk DML (Data Manipulation Language) operations, like INSERT, UPDATE, or DELETE, on collections in a single context switch between PL/SQL and SQL. This significantly reduces the overhead that comes from switching between the SQL and PL/SQL engines, especially when working with large data sets.

FORALL only supports INSERT, UPDATE, and DELETE statements, not SELECT.
It’s designed for bulk-binding collections to SQL statements, allowing these statements to execute efficiently on many rows at once.
The collection must be dense; otherwise, the code will raise an exception (use INDICES OF or VALUES OF if working with sparse collections).

DECLARE
   TYPE dept_tab IS TABLE OF NUMBER;-------------------------------------------dense collection
   dept_numbers dept_tab := dept_tab(10, 20, 30, 40, 50);
BEGIN
   FORALL i IN 1 .. dept_numbers.COUNT
      INSERT INTO departments (department_id)
      VALUES (dept_numbers(i));
   
   COMMIT;
END;

Using FORALL with Sparse Collections: INDICES OF and VALUES OF
When working with sparse collections (collections with gaps in the indices), you can use INDICES OF or VALUES OF clauses to handle non-continuous data.

INDICES OF: Allows FORALL to work on only the indices that exist in the collection.
VALUES OF: Operates on specific values in an index-by table collection.

DECLARE
   TYPE number_tab IS TABLE OF NUMBER INDEX BY PLS_INTEGER;
   numbers number_tab;
BEGIN
   numbers(1) := 100;
   numbers(3) := 300;  -- Note: index 2 is missing
   
   FORALL i IN INDICES OF numbers
      INSERT INTO my_table (num_column)
      VALUES (numbers(i));
   
   COMMIT;
END;

SAVE EXCEPTIONS is an option used with the FORALL statement to handle errors during bulk DML operations without halting the entire execution. Instead of stopping when it encounters an error, SAVE EXCEPTIONS allows the FORALL statement to continue with the remaining elements. At the end, you can retrieve information about any exceptions that occurred using the SQL%BULK_EXCEPTIONS collection.

This feature is particularly useful when you want to perform large updates or inserts and handle problematic rows individually, without losing all the progress on successfully processed rows.

How SAVE EXCEPTIONS Works
When you use SAVE EXCEPTIONS with FORALL, PL/SQL records each error and continues processing the remaining rows. After FORALL completes, you can check for any exceptions by examining the SQL%BULK_EXCEPTIONS attribute, which is an associative array of error details.

SQL%BULK_EXCEPTIONS(i).ERROR_INDEX: The index of the collection element that caused the error.
SQL%BULK_EXCEPTIONS(i).ERROR_CODE: The Oracle error code for the exception that occurred.
SQL%BULK_EXCEPTIONS.COUNT provides the total number of errors encountered during the FORALL operation.

Example of Using SAVE EXCEPTIONS
In this example, assume we have a list of employee IDs and new salaries, and we want to update them in bulk. However, some IDs may not exist in the employees table, which will cause NO_DATA_FOUND errors. Using SAVE EXCEPTIONS, we can handle these errors gracefully.


Explanation of the Example
Collection Declaration: We declare two collections, emp_ids and new_salaries.

FORALL with SAVE EXCEPTIONS: The FORALL statement performs a bulk update on the employees table.

The SAVE EXCEPTIONS clause tells PL/SQL to continue processing even if errors occur.
Exception Handling: If any errors occur, we catch them in the EXCEPTION block.

Loop Through Errors: Inside the exception block, we use SQL%BULK_EXCEPTIONS to loop through each error, displaying the index and the error message for each.

SQLERRM is used to get the full error message for each error code.
Important Points about SAVE EXCEPTIONS
Performance: Even with errors, FORALL ... SAVE EXCEPTIONS is still faster than processing rows individually because it reduces context-switching.
Error Indexes: ERROR_INDEX gives the index in the collection where the error occurred, so you can identify the exact data item causing the issue.
Multiple Errors: SAVE EXCEPTIONS allows capturing multiple errors in a single bulk operation.
Using SAVE EXCEPTIONS makes bulk operations more resilient and provides a way to handle errors gracefully, ensuring that successful operations proceed without disruption.

TRIGGER
=====================================================================================

In PL/SQL, a trigger is a stored procedure that automatically executes (or "fires") in response to certain events on a particular table, view, schema, or the entire database. Triggers are typically used to enforce business rules, maintain audit trails, automatically generate values, and perform complex validation.

Automated Execution: Triggers are invoked automatically when a specified event occurs. You don't need to explicitly call them in your SQL statements.

Event-Based: Triggers are tied to specific events like INSERT, UPDATE, or DELETE on a table or view.

Row-Level or Statement-Level: Triggers can be executed once per row (row-level) or once per SQL statement (statement-level).

Before or After: Triggers can be set to fire before or after an event, which determines whether the trigger executes before or after the operation (e.g., BEFORE INSERT, AFTER UPDATE).

Optional Condition: You can define conditions (e.g., WHEN clause) in a trigger to control whether it should execute based on the circumstances of the operation.

Types of Triggers
PL/SQL triggers are classified based on:

Timing: BEFORE or AFTER the triggering event.
Event: Specific DML operations (INSERT, UPDATE, DELETE), DDL operations, or system events.
Level: Row-level or statement-level triggers.
Common Types:
DML Triggers: Executed on DML events (e.g., INSERT, UPDATE, DELETE).
DDL Triggers: Executed on DDL events (e.g., CREATE, ALTER, DROP).
INSTEAD OF Triggers: Used for views, executed in place of DML on a view.
System Triggers: Executed on system events (e.g., LOGON, LOGOFF).
DML Trigger Syntax
Here's a basic syntax for creating a DML trigger:

1. Basic BEFORE INSERT Trigger
This trigger automatically sets a default value for a created_at column before a new row is inserted.

CREATE OR REPLACE TRIGGER set_created_at
BEFORE INSERT ON employees
FOR EACH ROW
BEGIN
    :NEW.created_at := SYSDATE;
END;

Explanation: :NEW is a reference to the new row being inserted. This trigger sets created_at to the current date and time (SYSDATE).

2. AFTER UPDATE Trigger for Audit Logging
This trigger logs any updates to the salary column of an employees table to an employee_salary_audit table.


CREATE OR REPLACE TRIGGER log_salary_changes
AFTER UPDATE ON employees
FOR EACH ROW
WHEN (OLD.salary IS DISTINCT FROM NEW.salary)
BEGIN
    INSERT INTO employee_salary_audit (emp_id, old_salary, new_salary, changed_on)
    VALUES (:OLD.emp_id, :OLD.salary, :NEW.salary, SYSDATE);
END;
Explanation: :OLD and :NEW are references to the old and new values in the row. This trigger fires only if there’s a change in the salary value.

3. BEFORE DELETE Trigger to Restrict Deletion
This trigger prevents deletion of employees from the employees table if they are managers.


CREATE OR REPLACE TRIGGER prevent_manager_deletion
BEFORE DELETE ON employees
FOR EACH ROW
BEGIN
    IF :OLD.job_title = 'Manager' THEN
        RAISE_APPLICATION_ERROR(-20001, 'Managers cannot be deleted.');
    END IF;
END;

Explanation: The trigger checks if the job title of the employee being deleted is 'Manager' and raises an error if true, thus preventing deletion.

4. AFTER INSERT OR UPDATE Trigger to Enforce Business Rule
This trigger ensures that any inserted or updated salary is greater than a specified minimum amount.

CREATE OR REPLACE TRIGGER check_minimum_salary
AFTER INSERT OR UPDATE ON employees
FOR EACH ROW
BEGIN
    IF :NEW.salary < 30000 THEN
        RAISE_APPLICATION_ERROR(-20002, 'Salary must be at least 30000.');
    END IF;
END;
Explanation: If the salary is less than 30000, an error is raised, enforcing a minimum salary rule.

5. INSTEAD OF Trigger on a View
This trigger allows INSERT operations on a view that joins multiple tables.

Assume there’s a view employee_department_view created from employees and departments.

CREATE OR REPLACE TRIGGER insert_employee_into_view
INSTEAD OF INSERT ON employee_department_view
FOR EACH ROW
BEGIN
    INSERT INTO employees (emp_id, name, department_id)
    VALUES (:NEW.emp_id, :NEW.name, :NEW.department_id);
END;
Explanation: When an INSERT is attempted on employee_department_view, this trigger redirects the insert to the employees table.

Trigger Scenarios and Applications

Audit Trail: Triggers can be used to log changes in important data, such as modifications to employee details, customer records, or financial transactions.

Enforcing Business Rules: Enforce constraints that may not be easily defined with standard database constraints, like complex checks across multiple columns or tables.

Automatic Data Adjustment: Automatically fill certain fields or adjust values before they are stored in the database, such as setting default values for timestamps or calculating derived values.

Cross-table Updates: Maintain data consistency by updating or inserting related records in other tables.
Considerations When Using Triggers
Performance: Triggers can impact performance if they perform heavy computations or operate on a large number of records in bulk operations.
Debugging: Triggers can make debugging more complex, as they execute automatically and may introduce unexpected behavior.
Transaction Control: Triggers cannot perform transaction control statements (like COMMIT, ROLLBACK).
Mutating Table Error: Row-level triggers on the same table as the triggering DML statement can cause a "mutating table" error if they try to query or modify the table being changed. Workarounds involve using AFTER triggers with PRAGMA AUTONOMOUS_TRANSACTION or storing data in package variables.
